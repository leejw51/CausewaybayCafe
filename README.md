# Causewaybay Cafe — Muse for the neighborhood restaurant

Install an AI café assistant on the owner's Mac. Guests scan a table QR and order in natural language; staff fulfill orders; owners manage the shop. Business data stays in local SQLite with a JSONL journal. **Model inference uses Meta's cloud API: this is locally hosted, not offline AI.**

Built for the Meta Global AI Developer Hackathon, **Build for Your World** theme.

For judging: [project brief, recorded demo guide and verification scope](docs/judge-brief.md).

## What to try

1. Guest: “We are three people. Pick three meals and three drinks for us.”
2. Muse uses the actual menu, availability, conversation history and recent shop orders to choose valid items.
3. The backend checks tool arguments, calculates prices and records the order. Logged-in demo guests pay from their local demo wallet; other guests pay through staff.
4. “What's my order?” reads the current database state. “Call staff” creates a service request.
5. **Picture my order** creates an optional Muse Image illustration. The item list is authoritative; illustrations can differ from actual servings.
6. Staff prepare and serve; the owner sees hourly/daily token usage and limits.

## Install and run on macOS

Prerequisites: Rust stable, the `wasm32-unknown-unknown` target, Trunk, Cap'n Proto compiler, Python 3.9+. Node.js is needed for browser tests, not normal operation.

```sh
rustup target add wasm32-unknown-unknown
# Install missing tools using your package manager, e.g. brew install trunk capnp
cp .env.example .env   # only for a fresh installation
```

Set `MUSE_API_KEY` and `CAFE_OWNER_WALLET` in `.env`. The owner value is a **public Ethereum address**, not a key or recovery phrase. Set `CAFE_PUBLIC_URL` to the URL guests can reach before printing QR codes.

```sh
make start             # demo service/payment mode; real on-demand guest Meta chat
make normaltest        # normal service mode
make status
make stop
```

Frontend: `http://127.0.0.1:8791`. Backend: port 8788. Both bind to `0.0.0.0` for local-network devices. Port 8790 is not used by the supervisor.

Phone microphone/camera access needs HTTPS. For local testing:

```sh
make tls TLS_HOSTS='localhost YOUR_LAN_IP YOUR_TAILSCALE_IP'
make start
```

Use `https://YOUR_LAN_IP:8792`. Install/trust the local CA on your test devices as described in [local HTTPS](docs/local-https.md). A self-signed certificate and a private Tailscale address are not a public judge-access solution.

Data, certificates and logs live under `~/.causewaybaycafe/`. SQLite migrations run automatically. The Python supervisor manages this checkout's frontend/backend processes. `make start` preserves data but explicitly selects demo service mode. Owner can change mode in Shop management.

## Roles and interaction

- **Guest:** QR session, chat or manual menu, basket removal, order status/cancellation subject to backend rules, staff calls. Optional mnemonic login enables a SQLite demo wallet; the HK$1,000 faucet requires login and grants once per wallet.
- **Staff:** order editing, preparation, serving and payment recording; service calls; menu drafts. Owner-only actions are checked server-side.
- **Owner:** staff appointment/revocation, menu publication, tables/QR printing, shop settings, API-key override and token budgets.

The topbar contains language, theme, font size, layout and More navigation. Horizontal guest layout places the order sheet on the right; vertical layout places it below. Conversations scroll internally while text and speech controls remain visible. Enter sends; Shift+Enter inserts a line break.

## Meta integration

| Capability | Implementation |
|---|---|
| Guest reasoning and tools | Muse Spark 1.3, native multi-turn tool calls with menu/history/order context |
| Menu-photo drafts | Meta vision → editable draft → owner publication |
| Menu and order illustrations | Muse Image 1.0; budgeted, cached order previews; no automatic paid retries |
| Guest speech input | Browser SpeechRecognition → same Meta chat path; availability depends on browser |
| Staff audio transcription | Meta Muse Voice Transcribe endpoint; physical-device capture still needs testing |

`MUSE_API_KEY` is used by default. An owner can override it through the management form. No secret is sent to the frontend. OpenAI/Grok are explicit optional alternatives, never silent fallbacks. Existing mascot artwork was generated using OpenAI; **order illustrations are generated by Meta**.

Guest chat and explicitly requested order pictures run immediately, independently of background Run. `CAFE_GUEST_AI=0` selects offline test fixtures; it is not the production conversational agent. `CAFE_MANAGEMENT_AI=1` (supervisor default) also allows Owner/Staff Meta chat in demo service mode after Run, so they can control virtual service conversationally. Automated tests force both AI flags off. Background AI and menu-image queues require Staff/Owner Run and check no more often than once per minute. Orders use server events, not periodic polling.

Usage is reserved before calls, reconciled with provider totals and bounded by hourly/daily limits. Missing usage is conservatively estimated. Image generation is limited to six requests per hour across the shop. Generated pictures are optional and never block ordering.

## Live tables and accelerated service

The staff/owner dashboard shows table IDs, seat counts and order states over an approximate seating map. Updates arrive through server events. It reports order activity, not physical occupancy.

In demo mode an Owner can start/pause virtual service at **1×, 10× or 100×**. The simulator creates only marked synthetic orders, advances preparation/serving/payment on a virtual clock, and never modifies real guest orders. It makes no AI calls; it stops on restart or when the shop becomes Live. Runs are bounded to 300 generated orders.

Owner can create/edit table counts and seats through forms or chat. In Live + Run mode, Shop management → floorplan accepts a photo. Meta vision returns an approximate draft with editable table IDs, seats and percentage positions. Owner reviews and confirms before application. Existing tables are not deleted; coordinates are not measurements or safety-approved plans. The source photo is not stored.

## Reliability and limits

The Rust backend validates role, ownership, item IDs, quantities and prices. Model output cannot execute SQL or arbitrary code. Checkout and demo-wallet deductions are transactional and idempotent. Guest turn IDs prevent accidental replay; interrupted paid calls are not blindly retried. See [agent architecture](docs/guest-agent.md).

This is a working prototype, not a certified POS/payment system. Wallet credits are demo balances, not cryptocurrency. Cash/card actions record a payment received outside the app. No payment gateway, tax reporting, inventory accounting or payroll is included. A shop GUID is metadata, not multi-tenant isolation. Some management labels and offline fixture replies remain English. Guest camera-to-order is not yet exposed as a completed flow.

## Validate

```sh
make test              # Rust unit/integration tests, no paid calls
make test-e2e          # isolated local browser suite
make simulationtest    # 12 complete synthetic service/payment flows
make stresstest        # tests plus 64 flows with 8 concurrent clients
make test-http3        # local QUIC integration test
# Explicit paid Meta checks:
cargo test -p cafe-server --test workflows live_meta_ -- --ignored --test-threads=1
cargo test -p cafe-server --test workflows live_guest_order_visual -- --ignored
```

Tests create disposable databases, never the owner's live SQLite file. Browser speech tests use a recognition stub; they do not prove physical microphone accuracy. See [submission/demo guide](docs/submission.md) and [verification history](docs/verification.md).
